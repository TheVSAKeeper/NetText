# Методика сравнения NetText и RustText на Windows

Парный стенд сравнивает NetText и официальный релиз RustText 2.6.1 на одном и том же `.NET 11` NativeAOT. Опубликованные результаты сохранены в [comparison.md](comparison.md) и [comparison-raw.json](comparison-raw.json).

## Запуск

Нужны интерактивный сеанс Windows x64, PowerShell 7, .NET 11 SDK, Visual Studio Build Tools с C++ x64 и Windows SDK. Клонируйте [RustText](https://github.com/Illson/RustText) рядом с репозиторием NetText (или укажите путь через `-RustTextRepository`):

```powershell
git clone https://github.com/Illson/RustText.git ..\RustText
pwsh -NoProfile -File tools\Measure-AvaloniaComparison.ps1
```

Стенд по умолчанию извлекает закреплённый релизный коммит RustText 2.6.1 (`6e7687d`) в каталог прогона и собирает обе программы в Release NativeAOT одним SDK (для других версий поддерживаются `-RustVersion <версия>` по тегу `v<версия>` и `-RustRevision <ref-или-sha>`). Исходники приложения NetText и скрипт сборки нативных библиотек сверяются с `HEAD` до и после сборки. Параметр `-Iterations` принимает чётное число, по умолчанию 6. `-Smoke -Iterations 2` проверяет сборку и измерительный контракт на небольших данных. Для полного прогона выделите не менее 12 GiB свободного места и не взаимодействуйте с запускаемыми окнами. Каждый запуск создаёт новый каталог в `artifacts/comparison/` или по указанному `-OutputDirectory`.

Пересчёт опубликованного отчёта из сохранённых данных:

```powershell
pwsh -NoProfile -File tools\Measure-AvaloniaComparison.ps1 -RenderFromRawJson
```

## GUI

- Сценарии включают пустое окно с пустым кэшем приложения и четыре тёплых случая: пустое окно, текст около 40 MiB, JSON около 10 MiB, лог около 10 GiB. Каждая попытка получает новый профиль. Для тёплого RustText стенд подставляет DLL из профиля прогрева. В холодном сценарии RustText извлекает DLL сам. Кэш ОС остаётся в естественном состоянии.
- Порядок сценариев перемешивается с записанным seed. Внутри пары приложения запускаются последовательно. Кто идёт первым, меняется от повтора к повтору.
- Время начинается непосредственно перед `Process.Start`. Стенд одинаково обнаруживает видимое окно процесса и фиксирует первый ответ на `WM_NULL`. Эти события характеризуют окно и его оконный поток. Отдельный контроль до среза памяти подтверждает фактическое открытие входного файла в ожидаемом режиме: для NetText – маркеры `document_ready_ms` (редактор) и `first_log_frame_ms` (лог), для RustText – заголовок окна и запись в `recent-files.json` нового профиля с полным путём и режимом (`line_count > 0` для редактора, `view_as_log = true` и `log.edit_pages = false` вместе с маркером `first_log_frame_ms` для просмотра лога). Неожиданный режим открытия отклоняет пробу. Внутренние маркеры, история профиля и заголовки подтверждают факт загрузки и фиксируют `readyMs` для сценариев с открытием файла.
- Working Set, peak Working Set и private bytes снимаются в одинаковом возрасте процесса, по умолчанию через 2000 мс. Срез включает фоновую работу, которую каждая сборка успела начать в своём режиме. Фактический возраст сохраняется в каждой записи. Отклонение более 100 мс, неверный режим файла или аварийное завершение оставляют запись с ошибкой и останавливают серию.

## Ядро

Стенд связывает исходники горячих путей обеих программ в одном процессе NativeAOT. Адаптер RustText использует его `LogDataReader` и настройки regex из `TextOperations`. Измерение характеризует поиск по строкам и не включает обработку вкладок, навигацию к совпадению и фоновую индексацию UI. Входы в памяти готовы до таймера. Проверки выходов выполняются после таймера в каждом повторе, включая прогрев.

| Сценарий | Что проверяется |
| --- | --- |
| Индекс лога | Конечное смещение и число разделителей при одинаковом файле, который заканчивается CRLF |
| Буквальный поиск | Полный проход без совпадений, единственное кириллическое совпадение у EOF, первые 32 попадания при частом совпадении |
| Regex | Промах с обязательным литералом, промах без извлекаемого литерала, совпадение у EOF без извлекаемого литерала |
| Форматирование JSON | Посимвольное совпадение с эталонным форматированием (отступы в 2 пробела и одинаковый стиль переводов строк) |
| Поиск и замена в редакторе | Полный список диапазонов на ASCII-входе, число замен и весь получившийся текст |

Для поиска по логу сверяются смещения всех попаданий, позиция остановки и статус завершения. Набор содержит короткие и длинные строки, ASCII и кириллицу. Для JSON и замены строк сравниваются публичные API со строковым результатом. Форматирование из снимка Scintilla с применением к окну остаётся отдельной задачей для E2E-замера. Байты аллокаций относятся к управляемой памяти измеряемого потока.

## Чтение результатов

`raw.json` содержит версии и хеши сборок, входов и файлов стенда, ОС, CPU, RAM, GPU/драйвер, диски, порядок и все повторы (в опубликованном [comparison-raw.json](comparison-raw.json) поля локального железа и дисков удалены). В `gui/` остаются отдельные записи, в `logs/` – аргументы, вывод и коды завершения сборок и прогона ядра. Готовый `report.md` показывает медиану и диапазон наблюдений, а для сравнения – медиану отношений внутри пар. Хвостовые задержки и переносимость выводов на другие машины требуют дополнительных независимых серий.
